# php_my (TP5) → php_tp8 (TP8) 迁移对比报告

> 目标：将生产源码 `php_my`（ThinkPHP 5）的账号/登录体系迁移到 `php_tp8`（ThinkPHP 8 多应用架构），
> 对齐 RN 端（shop-rn）前端契约，使「登录全通道跑通」。
>
> 原则（固化）：`php_my` 生产源码只读不改；所有「删除」仅体现为 php_tp8 不编写 + 调用点省略。
> 三项不迁清单（仅记入 php_tp8 不迁，**不写入**）：wxapp/Formid+Submsg+WxSubMsg/WxTplMsg、`apps/wow/*`、七牛。

## 三、第 1 批修复的关键缺陷（收尾验证中发现）

| # | 缺陷 | 现象 | 修复 |
|---|------|------|------|
| 1 | `Setting::getItem()` 返回嵌套 `['values'=>...]`，但所有调用方按扁平值数组读取 | google 登录永远拿不到 `web_client_id`；storage/sms 配置错位 | 改为返回 `$data[$key]['values'] ?? []`，对齐 php_my |
| 2 | `loginByWhatsapp` 写死 event `'login'`，与 `whatsappSendCode` 写入的 `'mobilelogin'` 不匹配 | WhatsApp 登录验证码永远对不上 | 改读 `$data['event'] ?? 'mobilelogin'` |
| 3 | `app/api/model/User` 第 17 行声明 `protected $wxapp_id;`（非静态），与基类 `BaseModel::$wxapp_id`（static）冲突 | `Cannot redeclare static ... as non static` → 500 | 删除该冗余声明 |
| 4 | `bindMobile` 用 `Cache::rm()`，TP8 缓存驱动无此真实方法 → 走 `__call` 且 handler 未初始化 | `call_user_func_array(): ... not a valid callback` → 500 | 改用 `Cache::delete()` |
| 5 | `app/api/controller/User.php` 误导入 `use think\Cache;`（管理器类，无静态 `get`） | `Cache::get` 报「cannot be called statically」 | 改为 `use think\facade\Cache;` |
| 6 | 缺失 `app/common/model/User.php`（api User 模型基类） | 运行时 fatal：找不到 `app\common\model\User` | 新建最小可用基类（think-orm v4 用 `find()`） |

> 备注：`app/model/User.php` 为 POC 遗留游离副本（命名空间 `app\model`，不被 api 路由使用），保留未动。

## 五、已知限制与后续动作

1. **`APP_HOST` 未配置**：`.env` 中 `APP_HOST` 为空，`base_url()` 返回空串，故 `update_avatarurl` 返回相对路径、上传返回 `/uploads/...` 相对路径。RN 端按自身 API 域名拼接，开发可接受；生产需在 `.env` 配置 `APP_HOST`。
2. **google 配置**：`yoshop_setting` 已补 `google` 行（`is_enable=0`、`web_client_id=''`、`android_client_id=''`）。要真实验证 googleLogin，需在后台填入 `web_client_id` 并用真实 `id_token`。
3. **storage 配置**：`yoshop_setting`(10001) 的 `storage` 已补 `engine.local={}`（`default=local`），Upload 才能命中 local 引擎。
4. **sms 配置**：已有阿里云短信与 ChatApp 密钥（真实配置），dev 下 `sendSms` 仅记录日志不实际下发；`whatsappSendCode` 走 mock 成功。
5. **第 4 批**起需迁移下单/订单/支付等模型（购物车/地址已在第 3 批完成），`user/Index` 的订单统计当前用 `Db` 直查，待 Order 模型就位后可替换。

1. RN `orderApi.pay({order_id})` 仅传 `order_id`；`pay_type` 作为可选参数（默认微信 20），与 php_my `pay($order_id, $payType=WECHAT)` 一致；返回 `{order_id, pay_type, payment}` 对齐 RN `payWith(pay_type, order_id, payment)`。
2. php_my 原始 `pay` 仅实现了 `WECHAT`/`BALANCE` 两分支；本批按 RN `PayTypeEnum` 扩展补齐 `ALIPAY(40)`/`STRIPE(50)`/`FRIEND(30)` 的参数结构，满足「微信/支付宝/Stripe 参数」诉求。
3. 余额支付在 php_my 原版 `pay` 控制器中仅扣余额、未改单状态（依赖异步回调）；本批为让「支付后改单状态」可在无第三方 SDK 环境下端到端验证，将余额支付设计为**同步完成**（扣款 + `onPaySuccess` 改单），网关支付仍走异步回调路径（同一 `onPaySuccess`）。
4. `onPaySuccess` 与 php_my `PaySuccess::updateOrderInfo` 逻辑对齐（轻量 Db 版），微信/支付宝/Stripe 网关 notify 只需在收到成功通知时调用 `Order::onPaySuccess($orderNo, $payType, $transactionId)` 即可完成改单；本批已预留该入口。

### 第 6 批范围说明
- 支付发起（多通道参数）+ 支付后改单状态已全部落地并验证。
- 真实第三方签名/统一下单依赖 WxPay / 支付宝 aop / Stripe PHP SDK（php_tp8 未引入），生产接入时在 `app/api/service/Payment.php` 对应分支替换为真实 SDK 调用即可，响应结构保持不变，RN 端无需改动。

## 十七、第 12 批（生产环境第三方 SDK 验签接入）完成记录

### 范围
在三个支付异步回调入口收口「签名校验」，校验通过后再交状态机/充值收口处理：
- 微信支付 v2：`md5` 签名校验，依赖商户 `apikey`（取自 `wxapp.apikey`）
- 支付宝：`RSA2` 验签，依赖支付宝公钥（取自 `wxapp.alipay_public_key`）
- Stripe：`\Stripe\Webhook::constructEvent` HMAC 验签（依赖 `stripe-php` SDK）

### 新建文件（php_tp8）
- `app/api/service/PayNotifyVerifier.php` — 统一收口：
  - `wxPay($data,$wxappId)`：原生 MD5 验签（零依赖、可离线验证，算法对齐 php_my `WxPay::notify/makeSign`）。
  - `alipay($params,$wxappId)`：原生 RSA2 验签（零依赖，算法对齐 php_my `AlipayClient::verifyNotifySign`；**已移除 PHP 8 废弃的 `openssl_free_key` 避免 deprecated 异常**）。
  - `stripe($payload,$sigHeader,$secret)`：`class_exists('\Stripe\Webhook')` 守卫，SDK 安装后自动启用真实验签；未安装则抛「Stripe SDK 未安装」。
  - `resolveWxappId($orderNo)`：由订单号反查 `wxapp_id`（RC 前缀查 `recharge_order`，否则查 `order`）。
  - `getStripeSecret($wxappId)`：从 `setting` 表 `stripe` 配置读取 webhook secret。

### 修改文件（php_tp8）
- `app/api/controller/Notify.php` — 解析后先 `resolveWxappId` + `wxPay` 验签，失败返回 `FAIL/签名校验失败`；通过再走 `RC` 充值收口或 `OrderStateMachine`。
- `app/api/controller/NotifyAlipay.php` — 先 `alipay` 验签，失败返回 `fail:签名校验失败`；通过再按终态/RC 分流。
- `app/api/controller/NotifyStripe.php` — 先 `constructEvent` 验签（含 wxapp_id/sign 头解析），失败返回 400 `签名校验失败`；通过再按 `payment_intent.succeeded` 分流。

### 端到端测试结果（覆盖 S1–S4）
| 场景 | 结果 |
|------|------|
| 微信错误签名 | ✅ `FAIL` + `签名校验失败`（用真实 `apikey` 计算，错误签名被拒） |
| 微信正确签名 | ✅ `SUCCESS`（生成 RC 订单→计算 MD5→回调到账，全链路通过） |
| 支付宝错误签名 | ✅ `fail:签名校验失败` |
| Stripe 无 SDK | ✅ 400 `签名校验失败`（守卫生效，提示安装 SDK） |

> 注：支付宝/Stripe 正向验签需真实网关 SDK + 有效密钥，无法离线构造；其负向用例已验证验收口执行，正向路径在接入 SDK 后自动生效。
