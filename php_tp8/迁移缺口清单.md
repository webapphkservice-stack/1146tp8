## 六、P0 补齐记录（第 13 批，2026-08-30）

### 6.1 真实支付接入（零 SDK 依赖）

三个渠道全部用原生 `curl` + `openssl` 实现，**没有引入任何 composer 依赖**，
与项目既有风格（第 12 批原生验签）保持一致。

**新增文件**

| 文件 | 作用 |
|------|------|
| `app/common/library/pay/PayConfig.php` | 支付配置统一入口（setting 表 > wxapp 表 > config/pay.php），不依赖全局 wxapp_id |
| `app/common/library/pay/WxPay.php` | 微信 v2 统一下单 + MD5 签名 + 通知验签，支持 APP / JSAPI |
| `app/common/library/pay/AlipayClient.php` | 支付宝网关客户端（RSA2 签名/验签）+ `sdkExecute()` |
| `app/common/library/pay/AlipayTrade.php` | `appPay()` 生成本地已签名 `order_string`；另含 query/close/refund |
| `app/common/library/pay/StripeClient.php` | PaymentIntent 创建（REST）+ **原生 Webhook HMAC 验签** |
| `config/pay.php` | 兜底默认配置（trade_type、币种、notify_url 覆盖） |

**修改文件**：`app/api/service/Payment.php`、`app/api/service/PayNotifyVerifier.php`、
`app/api/service/OrderStateMachine.php`（`deliver()` 支持写入物流信息）。

**关键修正**：原 `AlipayTrade::appPay()` 走网关取 `order_string`，但支付宝对该接口
**并不返回该字段**，导致原生 SDK 拿到空串无法拉起支付。已改为官方推荐的
`sdkExecute()`——本地拼接待签串并签名，不请求网关。

**验证结果**（7/7 通过，`e2e_p0_payment_test.py`）

| 场景 | 结果 |
|------|------|
| Stripe Webhook 正确签名 → 改单 | ✅ 200，`pay_status` 10→20 |
| Stripe 错误签名 | ✅ 400 签名校验失败 |
| Stripe 时间戳过期（重放） | ✅ 400 拒绝 |
| Stripe 重复回调（幂等） | ✅ 200 不重复累加 |
| 微信统一下单 | ✅ 真实调用网关，返回商户侧真实状态错误（说明**签名已被微信接受**） |
| 支付宝下单 | ✅ 返回真实签名 `order_string`（含 `sign=`） |
| Stripe 下单 | ✅ 真实调用 `api.stripe.com`，返回 `HTTP 401 Invalid API Key`（测试密钥） |

## 七、P1 补齐记录（第 14 批，2026-08-30：优惠券 / 积分抵扣接入结算）

### 7.1 背景与风险

原 `Checkout.php` 中 `coupon_money`、`points_money` 硬编码为 `'0.00'`、
`is_allow_points=false`，即**下单金额完全不含优惠**——用户领了券、有积分，
却仍被按原价扣款。属于「不报错但多收钱」的隐性资金风险。

### 7.2 实现（对齐 php_my `api/service/order/Checkout`）

**新增文件**

| `app/api/service/points/GoodsDeduct.php` | 实际使用积分按各商品最大可抵扣占比**分摊**，再换算抵扣金额 |

**修改文件**

| 文件 | 改动 |
|------|------|
| `app/api/service/order/Checkout.php` | 新增 `calcDiscount()` 统一计算入口（结算页与提交建单**共用**，杜绝两处金额不一致）+ 4 个子方法 |
| `app/api/model/UserCoupon.php` | 新增 `getUserCouponList()`（含最低消费门槛、生效时间、券面额折算）、`couponListApplyRange()`（适用范围）、`setIsUse()`（核销/退还） |

**关键设计：为什么分摊必须用「分」为单位**

按权重分摊必然产生小数。若直接以元做四舍五入，累计分摊额会与券面额对不上
（多扣或少扣用户钱）。改为以分为单位取整 → 余数逐件补齐，
可保证 `sum(各商品 coupon_money) === 券实际抵扣额`。
测试 D8 / D15b 专门校验这一点。

**修正的 php_my 原版缺陷**

`setGoodsListCouponMoneyDiff()` 原写成：

```php
$goods['coupon_money']++ && $tempDiff--;
```

当 `coupon_money` 为 0 时，后置 `++` 返回 0（falsy），`&&` **短路**，
`$tempDiff--` 不执行 → 余数永远分不出去 → 分摊总额少于券面额。
改为两条独立语句后，两商品场景 `8.58 + 11.42 = 20.00` 正确
（修复前会是 `8.58 + 11.41 = 19.99`，少抵扣 1 分）。
